# M6 Steady — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The person can see that a recording is still being sorted (and start sorting again), keep one file that holds everything and restore it on any phone, and trim a telling to the words that belong to it.

**Architecture:** A kit `SortingStatus` value fed by a `SortingReporter` the composition root owns (the worker, the live queues and the duplicate pass report activity and failures into it) and rendered as one line on the timeline and the Sessions screen; a re-entrant `SortingWorker.start()` called again from Settings, foreground and "Try again". A kit `Backup` type that writes and reads a `.lifeline` zip (ZIPFoundation) with a manifest, stages a restore and applies it at the next launch before the database opens, writing a safety copy first. A `retime` on `MemoryRepository` plus `CandidateActions.trimTelling` that also rewrites the card's span, with a sheet-held undo. Two flaky tests made deterministic first.

**Tech Stack:** Swift 6, SwiftUI, GRDB 7 (backup API for the checkpointed copy), ZIPFoundation 0.9.19 (new dependency, owner's call 0), Swift Testing, XCUITest.

**Spec:** `docs/specs/2026-10-23-m6-steady.md`.

## Global Constraints

- Nothing leaves the phone unless the person shares the file. The API key is never in the archive.
- Trimming never edits words or audio; it changes where a telling starts and ends, within its segment.
- Copy is fixed by the spec's Copy section (status lines, Settings, Change sheet).
- Export and restore are refused while a session is live or unlanded ("Finish your recording first"). A restore writes a safety copy first and is applied at the next launch. Refusal is by schema version, not app version.
- Kit tests: `cd ios/LifelineKit && swift test`. UI tests: `xcodebuild test -project ios/Lifeline.xcodeproj -scheme Lifeline -destination 'id=88EC5B09-3A30-4544-8145-F5246BB99AEE' -only-testing:LifelineUITests/<Class>`; run `xcodegen generate` in `ios/` after adding app or UI-test files or changing `project.yml`.
- Fixtures are invented; never a real person's words.

## Review Focus

1. A restore marker left by a crash between staging and launch: the next launch must apply it exactly once or discard an incomplete stage, never open a half-swapped directory. Task 4 (`applyPendingRestoreIsIdempotentAndSkipsAnIncompleteStage`).
2. Export while the sorting worker is mid-write: the copied database must be consistent (GRDB backup API, not a file copy) and the WAL must be checkpointed into it. Task 4 (`exportedDatabaseMatchesTheSourceUnderConcurrentWrites`).
3. A key saved while a pass is already running: the second `start()` must not run two workers over the same segments. Task 2 (`startWhileRunningIsANoOp`).
4. Trimming a span to zero or past its segment, or on a continuation part: refused with a plain error, the span untouched. Task 6 (`retimeRefusesEmptyAndOutOfSegment`).
5. A restored archive from an older schema with an audio file missing: the app opens, migrates, and the memory's Play says the recording is missing rather than crashing. Task 5 (UI: `testRestoreFromAnOlderCopyMigratesAndOpens` uses a v7 fixture archive without one audio file).
