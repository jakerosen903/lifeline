# PC-d rulings

- **D1.** Ruling: `MentionOut.init` keeps the argument `likelyAliasOfPersonID`, with a default of nil; the schema and the prompt drop the key, and the decoder ignores it — the plan's removal would touch about ten call sites for no gain — if wrong, a later commit removes a dead argument.
- **D2.** Ruling: when the app does not build after Task 4 because of the chip id, the change to `WhoIsThisViewModel` moves from Task 5 into Task 4 — each task must leave the app building — if wrong, one file is reviewed a task early.
- **D3.** Ruling (Task 1): `OutputValidator.Validated` gains `people: [PersonOut]`, the people that passed (first of each handle, said name in the segment, handle not blank), with a default of [] in its init — "dropped" needs a list to drop from, and Task 3's `HandleResolve` reads the validated people — if wrong, Task 3 reads `output.people` and re-applies the same checks.
- **D4.** Ruling (Task 1): `extractor.v8.md` also names `recordingPeople` in its Context paragraph, beside the new rule 8 — the paragraph lists what the packet holds and would be wrong without it — if wrong, one sentence of the prompt is removed.
- **D5.** Ruling (Task 2): the packet filters a handle's person id after the budget trim, not only after the 50-person cap, and keeps the first id given for a handle — the model must never get an id for a person it was not shown — if wrong, a later valid id for that handle is not sent, and the guess runs with no model pick.
- **D6.** Ruling (Task 3): `HandleResolve` gives one `handlePeople` entry per handle when a memory lists a handle twice, and clears an unknown person id in the output's `people` as well as on each card — a handle is one person, and no unchecked id should stay anywhere in the output — if wrong, a duplicated handle shows one chip instead of two.
- **D7.** Ruling (Task 3): `removingOwner` also drops a person mention whose `handle` is the owner's handle, and turns an `about_ref` equal to that handle into `self` — the owner is never a person, whatever words the mention uses — if wrong, an owner mention said another way ("me") is lost instead of waiting as a card.
- **D8.** Ruling (Task 3): a continuation adds each new handle to the earlier card's `handlePeople` and `personHandles`, but does not touch its `peopleRefs` — today's continuation code never merged `peopleRefs` (Keep merges the continuation row's people itself), and `CarriedName` reads `personHandles` — if wrong, Task 4's Keep may see a continuation's person both on the earlier card and on the superseded row, and must dedupe by handle.
- **D9.** Ruling (Task 4, R-4a): Keep, the preview and both Same story paths share one `tellingEdges`, so `MergeActions.swift` changed — D8 needs one handle plan across a card and its rows — if wrong, one helper is split again.
- **D10.** Ruling (Task 4, R-4b): a person planned for a handle joins another planned person only by contact, never by title (`EntityRepository.Write.handlePersons`) — two new people with one name must stay two — if wrong, one set and one guard are removed.
- **D11.** Ruling (Task 4, R-4c): Same story into a memory of another recording writes no handle — a handle has no meaning in another recording — if wrong, such a link groups by said name.
- **D12.** Ruling (Task 4, R-4d): a handle the recording already linked follows its newest kept link — after a move the newest link is the owner's latest state — if wrong, a later card follows a single moved link.
- **D13.** Ruling (Task 4, R-4e): a contact that a person planned for another handle of the same said name was made from is left out of the guess — a planned person is not yet on file, so `taken` cannot hold them — if wrong, none found.
- **D14.** Ruling (Task 4, R-4f): `choices(for:)` reads the stored key as it is — keying it again would lowercase a handle; older rows were stored normalized — if wrong, a hand-written old row with other casing is not found.
- **D15.** Ruling (Task 4, R-4g): `aboutEntity` checks a handle before an entity id and a mention ref, and follows a handle linked earlier in the recording — handles ("p1") and mention refs ("t1") are separate spaces — if wrong, a mention ref equal to a handle reads as the handle.
- **D16.** Ruling (controller, after Task 4): Task 5 also makes `separateTelling` find a telling's people by handle when the links have handles; plan decision 9 left it on the said name — two handles of one name in one memory are two links with one said name, so the said name moves both or neither — if wrong, one function goes back to the said name.
- **D17.** Ruling (controller, after the Task 5 review): a handle of the recording so far is valid in `person_handles` and `about_ref` without a `people` entry in that output; the card stores the recording's entry with its first said name; Keep follows such a handle also for a fact with no people of its own (Task 4b) — the plan's validator rule rejected "She was always late" about a person named one segment earlier, which is the case a handle exists for — if wrong, a chip can show a name that was said in an earlier segment of the recording, not in this one.
- **D18.** Ruling (Task 5, R-5a): a link with no handle groups only with links with no handle of the same said name — the group must be one set whichever link is tapped — if wrong, a hand-made link in a recording with handles is settled alone.
- **D19.** Ruling (Task 5, R-5b): a link with a handle also takes a detail whose mention has no handle, by the said name — a detail card with no handle has no other evidence — if wrong, a move carries one detail too many in a mixed recording.
- **D20.** Ruling (Task 5, R-5c): `separateTelling` uses handles only for a telling in the memory's own recording — D11 drops handles across recordings — if wrong, the said-name rule applies there, as before.
- **D21.** Ruling (Task 5, R-5d): a link with a handle and no said name groups by its handle — the handle alone names the person — if wrong, one guard.
- **D22.** Ruling (controller, after the Task 4b review): a handle in `about_ref` is always also one of that memory's people. The `v8` prompt says so, and `HandleResolve` adds an `about_ref` handle to the memory's `personHandles` when the model left it out — then the card stores the person, and Keep's guess works whatever the owner keeps first — if wrong, a fact shows a chip for the person it is about that the model did not list.
- **D23.** Ruling (Task 4b, R-4b-a and R-4b-f): the recording's entries go on memories only, never into `Validated.people`, and a recording entry's person id is checked again against the packet's people — `people` keeps its meaning (this output's people) — if wrong, none found.
- **D24.** Ruling (Task 4b, R-4b-b to R-4b-e): Keep reads the recording's handle links for every card that is not a moment and has an `about_ref` other than `self` (`mayFollowAHandle`); a dropped own entry falls back to the recording's; a recording entry with no said name is skipped — a handle never equals an entity id or a mention ref (D15) — if wrong, one extra read per fact card.
