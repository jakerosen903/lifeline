# Rulings — plan: docs/plans/2026-11-18-people-contacts-b.md

- PB1 (controller, pre-flight): Task 2 updates every app call site of `PersonChipLine.text` so the app builds, passing `fromContact` from the link or chip and `contacts: .none`. Task 5 passes the real value from the cache. — Why: each task must leave a building app. — Cost if wrong: none; a temporary value.
- PB2 (controller, pre-flight): a person the app made from a contact on Keep (rules 3 and 5), with `created_by_guess` still true and `name_origin` still `contact`, counts as an empty guess when a move leaves them with nothing: the contact was the app's choice. A contact the owner linked always keeps the person. The spec's "no contact" in "Moving a name" point 6 is narrowed to "no contact the owner linked". — Why: principle 9, no person without a story. — Cost if wrong: a wrong guess from contacts leaves no empty person behind; the owner who wanted that person must link again.
- PB3 (controller, pre-flight): `created_by_guess` is cleared only by an owner's action. The owner's `link` clears it. `reguess` and Keep, which are the app's actions, do not. — Why: PC-a ruling R39 and plan decision 9 of PC-a. — Cost if wrong: an empty person the app linked by itself is removed by a later move.
- PB4 (task 1): `ScriptedContactsDirectory` init is `(cards:pictures:access:accessAfterRequest:)`; `accessAfterRequest` defaults to `access`, is what `requestAccess()` returns and then becomes the access; `failsOnRead` makes all three reads throw. Locks use `Synchronization.Mutex`. `ContactSearch` matches a prefix of any word of the four name fields, sorted by folded full name. — Why: the brief left them open. — Cost if wrong: a rename in later tests.
- PB5 (task 2): Keep's plan carries the said name of a person made from a contact in `EntityRepository.Write.aliases`, written in the memory's own transaction. `Write.apply` never saves the display name of a person whose `name_origin` is `contact` as an alias. — Why: a kill leaves the person and their one alias together, and a contact's name cannot become an alias by this path. — Cost if wrong: none; one more field on the plan.
- PB6 (task 2): "the oldest alias" is the alias table's rowid order, read by `PeopleRepository.aliasesOldestFirst(of:)`; `ExtractionQueue` passes aliases in that order and `ContextPacketBuilder.build` expects it. The backup copies pages, so rowids survive; the app never runs VACUUM. A person from a contact with no alias is left out of the packet. — Why: `Alias` has no timestamp and a migration is out of scope. — Cost if wrong: a VACUUM added later could renumber rowids; the packet name would become another said name, still the owner's words and never the contact's.
- PB7 (task 2): a person Keep makes from a contact gets one alias, the said name of the first ref that reached the contact (`SaidName.name`, never the relation phrase). A second ref of the same card that reaches the same contact reaches the same planned person and adds no alias, as any `assumed` link adds none. Two segments of one telling that each plan the same contact merge by entity title and keep both said names. — Why: the spec's one exception to the alias rule is the said name. — Cost if wrong: a second said name in one card is not learned until the owner settles.
- PB8 (task 2): `PersonLink.personFromContact` and `PreviewChip.fromContact` are the person's state (`name_origin` contact and `created_by_guess`), as the brief defines them. So a later recording's rule-4 guess to that person also reads "Assumed · new, from your contacts" until the owner settles or moves a link to them. — Why: the brief's signature has no per-link flag. — Cost if wrong: "new" shows on a person who is no longer new; a per-link flag would need a column.
- PB9 (task 2): `removeIfEmptyGuess` still requires `contact_photo_id` nil, and a photo link still holds the person. Task 3 decides whether the copied contact picture keeps a Keep-made person. Undo of a move that removed a person from a contact is refused (`stale`) when another person holds that contact now, before the unique index would fail. — Why: PB2 without deciding Task 3's picture rule here. — Cost if wrong: after Task 3, a Keep-made contact person with a copied picture is never removed by a move.
- PB10 (controller, task 2 review): no text that goes to a model may hold the name of a person whose `name_origin` is `contact`, on any path: the context packet, a curiosity question, the interviewer's context, the resolver. One kit helper gives a person's name for the model (the oldest alias for a person from a contact; nil when there is none, and then the person is left out or the question is not drafted). A rename of a person from a contact does not save the contact's name as an alias. — Why: the Global Constraint "nothing from a contact goes to the model", and the usage string the owner reads. — Cost if wrong: the model does not see a full name the owner never said.
- PB11 (controller, replaces PB8): the line "Assumed · new, from your contacts" shows only on links in the recording of that person's first link. A later recording's guess to the same person reads "Assumed · you said “{said name}”". — Why: "new" is false in a later recording. — Cost if wrong: one more read for a chip.
- PB12 (controller, answers PB9, for Task 3): the picture the app copied from a contact (`contact_photo_id`) does not keep a person the app made from a guess. When a move removes that person, the photo link goes with the entity and the photo row waits for the launch sweep, as other homeless photos do. Undo within its 6 seconds restores the person, `contact_photo_id` and the photo link. A photo the owner added keeps the person. — Why: PB2; the copy was the app's act. — Cost if wrong: none for the owner's own photos.
- PB13 (controller, task 2 review): `EntityRepository.Write.merge` joins two planned persons that have the same `contactIdentifier`, whatever their titles, and never joins two planned persons with different contact identifiers. — Why: the unique index would throw and the owner would lose a Keep. — Cost if wrong: none known.
- PB14 (task 2, fix round 1): the PB10 helper is `NameForModel.of(_:aliasesOldestFirst:)` (pure), with `PeopleRepository.namesForModel()` and `nameForModel(of:)`. It feeds the packet's people, the entity curiosity question (`EntityCuriosity.drafts(personNames:)`; a person with no name is not asked about, and an open question for them is closed by the next resolver run), and the interviewer's opening: `SessionSubject.modelTitle` (the old init sets it to the title; the person page passes `nameForModel`, nil until its first refresh). A subject with no model title gets the plain tab opening, as one kept from the AI does. The record bar still shows the page's title: it is on screen, not sent. — Why: the opening is sent to the interviewer in `InterviewerRequest.opening`. — Cost if wrong: a person page of a contact person with no said name opens plainly.
- PB15 (task 2, fix round 1): "the recording of the person's first link" is the session of the first span of the person's oldest linked memory (by `memory.created_at`, then id), any relation. A link whose memory has no span, or a person with no link, counts as the first recording. Within one plan and across plans, a person planned from a said name never joins a person planned from a contact by title (PB13 applied to both sides). — Why: the brief left them open. — Cost if wrong: a moment moved in from an older recording would make that recording "first".
- PB16 (task 3): `PhotoLibrary` gains an internal `addNotingNew(fileAt:assetLocalID:to:now:) -> (photo, isNew)`; `add` keeps its signature. `copyPicture` records `contact_photo_id` only when `isNew`, and only while the person still holds that contact with no copy; a copy that cannot be recorded is removed again. `link` writes the fields in one transaction, then copies the picture; a picture read or store that fails does not fail the link (the fields stay), and a later `copyPicture` fills it in. The internal `link(_:to:clearingGuess:)` is the app's link for Task 4. — Why: the library had no way to tell a reused photo from a new one; a link the owner made must not read as failed because of a picture. — Cost if wrong: a failed picture is silent until something calls `copyPicture` again; Task 4's launch check should call it for each linked person with no copy.
- PB17 (task 3): a link to another contact removes the old copy's photo link and, when no other page holds it, its row in the link's transaction; the file is deleted after the commit (a kill leaves a file with no row, which the sweep takes). Linking the same contact again changes nothing. `unlink` leaves `created_by_guess` as it is (the brief names only the four contact columns). — Why: one transaction for the fields and the old copy. — Cost if wrong: a person Keep made from a contact and then unlinked can still go as an empty guess (its name origin stays `contact`).
- PB18 (task 3, PB12): `removeIfEmptyGuess` ignores the photo link of `contact_photo_id` when it counts what holds a person; the receipt keeps that link's role and order (`PersonMoveReceipt.removedContactPhoto`) and Undo restores `contact_photo_id` and the link. When a sweep has taken the homeless photo row before Undo, Undo restores the person without the picture (`contact_photo_id` null). — Why: PB12; a refused Undo would lose the person for a picture the app made. — Cost if wrong: none known.
- PB19 (controller, answers PB17): `unlink` is the owner's action, so it clears `created_by_guess`. A person the owner unlinked is never removed as an empty guess. Task 4 makes the change. — Why: PB3. — Cost if wrong: an unlinked person with no story stays in People until the owner deletes them.
- PB20 (task 3, fix round 1, replaces PB16's `addNotingNew`): the contact's copy is one transaction: the photo row, its link to the person and `contact_photo_id` (`PhotoLibrary.addRecordingNew(fileAt:to:now:recordNew:)`, whose `recordNew` runs inside `PhotoRepository.insert(_:linkingTo:alsoWriting:)`). The record keeps its guard (still that contact, no copy yet); when it fails it throws, so the photo rolls back and `copyPicture` returns quietly. A reused photo is linked and never recorded. — Why: two transactions let a kill leave the app's copy looking like the owner's photo for good. — Cost if wrong: none known; the file written before the transaction is swept at launch after a kill.
- PB21 (task 3, fix round 1): `PersonMoveReceipt.ContactPhotoLink.role` keeps the stored text of `photo_link.role` as it was, not a `PhotoRole`, so Undo writes back exactly what the move removed; no Undo is refused over a role. — Why: this loses nothing; refusing would lose the person for an unknown role. — Cost if wrong: none.
- PB22 (task 4): `check()` reads the linked identifiers in one batch; an identifier with no card of that identifier in the batch is read again alone, and the card that read returns is the unified card (its identifier is stored). The batch read throws before any write. A single-identifier read comes later and can throw after earlier people were followed; each person's write is one transaction and valid on its own, and the next check finishes the rest. A picture that cannot be read or stored is skipped (`try?`) and the next check tries again (PB16). `ScriptedContactsDirectory` gains `merged` (old identifier → current card) and `allReads`, and answers nothing under `notAsked`/`denied`. — Why: the real system returns unified cards with no map back to the asked identifier; a single-identifier read is unambiguous. — Cost if wrong: one extra read per unified or missing contact per check.
- PB23 (task 4): when the card the system returns for a stored identifier has an identifier another person holds (two linked cards unified), this person's state becomes "missing" and nothing else changes; the owner relinks or unlinks. When two linked cards unify into a card with a new identifier, the first person in the check's order (`linkedPersons()`, by name) takes the new identifier and the second is "missing". — Why: the unique index allows one holder; the order is the check's, not a judgement of who is right. — Cost if wrong: a person shows "not in your contacts" though the card exists under the other person.
- PB24 (task 4): "New picture" compares the bytes before the store: a picture whose bytes are any stored photo changes nothing, so the replacement never claims the owner's photo and never links one; a person with no copy goes through `copyPicture` instead, which links a stored photo with the same bytes (wherever it is stored) without recording it, as on a link (PB20); a contact whose picture was removed keeps the copy. The replacement is one transaction (new row and link, `contact_photo_id`, `setCover`, the old copy's link and its row when homeless), guarded on the person still holding the identifier and the copy being first; the old file is deleted after the commit. — Why: plan decision 10 and the kill rule; the spec names only a new picture. — Cost if wrong: a contact's picture removed in Contacts stays on the page until the owner removes it.
- PB25 (task 4): the name re-link of a missing contact and `ContactSuggestion.pick` both drop held (and, for pick, declined) cards first, then require exactly one. The re-link compares the full name only (spec, "The identifier"); `pick` compares full name, given name and nickname, the names rule 5 matches by. — Why: the dispatch's "exactly one visible contact, not held by another"; a person named by a first name would otherwise never get a suggestion. — Cost if wrong: a suggestion for a first-name person the owner declines with one tap.
- PB26 (task 4): `reguess` leaves the person out of the people the guess reads (they hold the said name and would find themselves by rule 4), takes the said name of the person's first `new` link in the session, adds that said name and the name the person was made with as aliases (both the owner's words), stores the trimmed full name as `contact_name` as Keep does, and changes only the person's `new` mention links in that session. A contact with an empty full name is not linked by `reguess`, and in `check()` such a contact leaves the person's name as it is. — Why: the brief left them open; a page never loses its title. — Cost if wrong: none known.
- PB27 (task 5): `reguess` returns `ContactLinkActions.Reguess` (`changedLinks`, `linkedPeople` in link order) in place of an `Int`, so the landing copies the picture of each person it linked. A person counts as linked only when the write changed one or more links. — Why: the brief's Step 2 needs the people; a follow-up read could not tell this look's links from older ones. — Cost if wrong: none; Task 4's tests read `.changedLinks`.
- PB28 (task 5): `keptPeopleInSession` is `PersonLinkRepository.keptPeopleCount(in:)`: mention links of the session's memories (first span) to any person but the owner, any origin. The landing asks from `LandingScreen`'s `.task(id: keptPeople)`, not from the view model's init, so the system prompt shows over the landing and again when a kept moment first names a person; a flag on the view model stops a second ask. — Why: spec "Access": the first kept moment that names a person, on that recording's landing. — Cost if wrong: a landing whose only links are details does not ask.
- PB29 (task 5): "asked before" is the `UserDefaults` key `contacts.accessPromptShown`, set before the system prompt shows (a kill while it is up does not ask again); `-uiTesting` removes it at launch, as it does `LifelineSpeaks.key`. Scripted access: no `-uiTesting-contacts` (or an unknown value) is `notAsked` with a request answered `denied`; `notAsked` named is answered `full`; the other values are kept after a request. — Why: existing UI tests see no contacts and no change; the prompt test is repeatable. — Cost if wrong: none outside UI tests.
- PB30 (task 5, PB1): `PersonChipLine.ContactsSeen.of(saidName:access:cards:held:)` (kit, pure) uses the name part of `SaidName` and the names rule 5 matches by (full, given, nickname); "free" means no person holds the identifier (a person in the "missing" state still holds theirs). A said name with no name part is `noMatch` under access. The chip row reads the held identifiers with the covers in a `.task` keyed on each chip's id, person and origin, and scans only `new` chips. — Why: one pure rule with a test; the landing body re-runs each second while sorting. — Cost if wrong: a `new` chip can read "not linked yet" for a contact a person took moments ago, until the row's chips change.
- PB31 (task 5): `ExtractionQueue`'s own `CandidateActions` is used only for `acceptMention`, which runs no guess, so it gets no closure and the kit gains no parameter. — Why: neither Keep nor the preview goes through it. — Cost if wrong: none today; a later use of that instance for Keep would guess without contacts.
- PB32 (task 5): the launch check starts from `RootView`'s `.task` (`AppModel.firstScreenShown`), never in `AppModel.init`. One `ContactsCheck` actor (app, its own file) refreshes the cache, then calls `check()`; a request while one runs makes one more run after it. Only `SystemContactsDirectory` is observed for `CNContactStoreDidChange` (`SystemContactsDirectory.didChange`, so no other file imports `Contacts`). A failure logs the error's type only. — Why: a burst of change notices must not run checks side by side; an error's text could carry a name. — Cost if wrong: none known.
- PB33 (task 5): `SystemContactsDirectory` holds nothing and makes a `CNContactStore` per read inside a detached task, so it is `Sendable` and nothing touches the system until a method runs. Without access its reads answer empty or nil, as the scripted one does. `picture` of a record that no longer exists is nil. Names come from `CNContactFormatter`'s full-name descriptor plus given, family, middle, nickname and `imageDataAvailable`; pictures read `imageData`, then the thumbnail. `PersonMoveUndo` now takes a `PersonLinkActions` built by `Dependencies.personLinkActions()`. — Why: Swift 6 concurrency; the brief's "no construction without the closure". — Cost if wrong: a store per read costs a little more than a shared one.
- PB34 (controller, task 4 review): under limited access the check does not re-link a missing contact by name; it only marks the person missing. Under full access the re-link by name stays (spec call 12). — Why: under limited access the app sees only the shared contacts, so "exactly one with that name" can be a namesake, and the re-link would replace the right person's picture with the namesake's. The spec says a person whose contact is no longer shared keeps everything. — Cost if wrong: after a restore on a new phone with limited access, the owner links again by hand.
- PB35 (controller, task 4 review): `reguess` does not link a contact the owner declined for that person. — Why: "No" is kept. — Cost if wrong: none known.
- PB36 (task 4, fix round 1): `contact_name` is the trimmed full name on every write (`ContactCard.keptName`: link, check, Keep, `reguess`). `followContact` writes only what changed, and `markContactMissing` only a state that is not "missing", so a check of unchanged contacts writes nothing (a test counts the connection's changes). Under full access a re-link by name whose card has another picture is silent, then the picture follows "New picture" (the copy is replaced while it is first). — Why: PB34 review; a launch check runs every launch. — Cost if wrong: none known.
- PB36 (controller, task 5 review): the landing does not show the contacts prompt on a recording that was heavy or where a serious disclosure showed. It asks on the next landing that qualifies. — Why: PRINCIPLES, safety and "every session lands"; a system dialog must not follow a serious disclosure. — Cost if wrong: the prompt comes one recording later.
- PB37 (controller, task 5 review): the "asked" flag is set after the system answers, not before. A force-quit while the prompt shows lets the app ask again. No log line holds an error's text from a contacts path; it logs the error's type only. — Why: PB32's own rule; and the owner must not lose the only way to give access. — Cost if wrong: none known.
- PB38 (task 5, fix round 1, PB36): the landing is "quiet" for the contacts prompt only when it is not heavy, shows no serious disclosure, and sorting is done (`LandingViewModel.isQuietForContacts`); the screen's task is keyed on the kept-people count and that value, so the prompt shows when sorting ends. A "New" chip's contacts line is worked out in the chip row's `.task(id:)` (keyed also on the access and the cache's size) and in `EntityViewModel.refresh` for `new` links only, never in `body`. — Why: a flag from a segment still sorting can make the recording heavy after a kept moment names a person; the landing re-renders each second while sorting. — Cost if wrong: the prompt waits for sorting to end; a chip shows "New" for one frame before its line.
